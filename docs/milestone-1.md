## Observations

Dated because these are undocumented Microsoft interfaces.

- 2026-10-17: unauthenticated `GET /organizations/oauth2/v2.0/authorize` with the public client ID returns the normal sign-in page (`sErrorCode` 50058, "not signed in") for every redirect tried, including obviously invalid ones. Redirect validation happens after account selection, so step D needs a real sign-in. An unknown client ID returns 50059 instead.
- 2026-10-17: opening `https://login.microsoftonline.com/common/oauth2/nativeclient?code=…` in a normal browser shows an anti-phishing warning ("This page is not normally shown and could be a sign of a phishing attempt … do not copy or share the URL") and after 3 seconds redirects to `/common/wrongplace`. FreeRDP's terminal `Browse to:` / `Paste redirect URL here:` flow is therefore not usable by people any more. Copying the code with browser developer tools would work around this protection, so we don't use or document it (spec §4 step 4). Consequence: with the public client ID, sign-in needs a web view that catches the redirect before the page loads (as the reference app does), unless the loopback redirect test (step D) succeeds.
- 2026-10-17: a normal browser that is already signed in to another Microsoft account (here a personal Microsoft 365 account) picks that account automatically for the FreeRDP authorize URL, which has no `login_hint`. The app's per-account sign-in cookies (spec §6) avoid this; research tests use a private browser window.
- 2026-10-17 (reference app log, owner's tenant): the gateway token via `Browse to:` worked (answered by the reference app's hidden web view, not by copying); RDSTLS then failed with `0x0000052E`. See [0005](adr/0005-password-login-host-pools.md).

- 2026-10-17 11:54 (reference app, owner's tenant, Advanced flags `/d:AzureAD`, password typed by hand into FreeRDP's SDL dialog): again `RDSTLS_RESULT_LOGON_FAILURE [0x0000052E]`. Both failures share a hand-typed 32-character password. Next: the same with the password pasted via `research/reference-app-paste-password.sh` (`FREERDP_ASKPASS`), first with `/d:AzureAD`, then with no Advanced flags.
- 2026-10-17 12:13 (reference app, `/d:AzureAD`, password pasted via `FREERDP_ASKPASS`, no dialog): `0x52E` again, 10 s after the gateway step. A typing error is now unlikely.
- FreeRDP history: commit `967793134` (2025-09-26, "[core,arm] fix domain setting"): "While AzureAD seems to be required for many setups, some need an empty domain (or maybe a different all together?)". FreeRDP issue #11887 (fixed in 3.18): an AVD setup that needed an empty domain; the same reporter also connected by forcing Entra authentication to the session host (`enablerdsaadauth:i:1`) although the host pool didn't set it. Issue #10298: `RDSTLS_RESULT_LOGON_FAILURE` with several formats; the maintainer calls the right format "hard to determine". No later FreeRDP change to `arm.c`/`rdstls.c` addresses this (checked `3.32.2..master`).
- Next tests: (1) empty domain (no Advanced flags) with a pasted password; (2) Advanced flags `/sec:aad` (Entra authentication to the session host, no password).
- 2026-10-17 14:23 (the app itself, native build, COSMIC Wayland): sign-in through the WebKitGTK helper with the public client ID, code exchange with PKCE, ID token validation, feed discovery and all tenant feeds succeeded on the owner's account: 3 workspaces, 3 desktops listed. The feed service accepted the public client ID with `X-MS-User-Agent: com.microsoft.rdc.html/2.0.79.2 rdhtml-sdk/2.0.4`.
- 2026-10-17 14:45–14:46 (the app, native build): Connect reached the session host. The AVD gateway token came from our sign-in helper in FreeRDP mode without showing a window (cookies from the app's sign-in). RDSTLS then returned `RDSTLS_RESULT_LOGON_FAILURE [0x0000052E]` with the password pasted into the app's dialog, both with logon setting *Empty domain* and *Automatic* (`AzureAD`). With the reference app's `/d:AzureAD` + pasted password (12:13) the result was the same. Not yet tried: *Entra sign-in* (`/sec:aad`) and a custom (on-premises) domain.
- 2026-10-17 15:04 (the app, debug build): after the owner **changed the password**, a pasted new password still gave `RDSTLS_RESULT_LOGON_FAILURE [0x0000052E]` (retried once, same result). A wrong or mistyped password is now ruled out as the cause. FreeRDP 3.32.2 `arm.c` re-read: the service's `redirectedUsername` always replaces `/u:`, so only the domain is under client control; with `/sec:aad` FreeRDP skips RDSTLS entirely (`arm_fill_gateway_parameters`). Remaining suspects: a policy that blocks password logon to the session host (for example per-user MFA or Conditional Access on Entra-joined hosts without SSO), or session hosts joined to an on-premises domain. Next test: *Entra sign-in*.
- 2026-10-17 15:16 (the app, debug build): **Entra sign-in (`/sec:aad`) connected** to the owner's host pool and showed the desktop, although the `.rdp` file has no `enablerdsaadauth`. This matches the owner's experience with the official Windows and macOS apps, which never ask for a Windows password. The password logon (`0x52E` with every domain setting and a new password) is blocked on the host side; the client can't fix it. Consequences: Entra sign-in is now tried first for every desktop (ADR 0005, revised).
- 2026-10-17 15:16: before the desktop appeared the owner had to sign in 2–3 times (app sign-in, then FreeRDP's gateway and session-host tokens). Cause: FreeRDP 3.32.2 starts a new helper process per token request (`client/common/client.c`, `aad_auth_helper_start` per call), and Microsoft's sign-in cookie is a session cookie that WebKit keeps only in memory. Fix: the helper shares session cookies through `$XDG_RUNTIME_DIR/cosmic-ext-avd-web/` (`signin/src/session_jar.rs`).
- 2026-10-17 15:16: the remote desktop kept its initial size inside a larger window (black area). Cause: COSMIC auto-tiling resizes the window before the display control channel is up, and FreeRDP 3.32.2's SDL3 client sends no layout on the first activation of a windowed session (`client/SDL/SDL3/sdl_disp.cpp`, `OnActivated` returns early when `firstActivation`; `DisplayControlCaps` only makes the window resizable). Any later window resize sends the layout. Upstream fix candidate: send the layout in `DisplayControlCaps` for windowed sessions too.
- 2026-10-17 15:33 (the app, Entra sign-in remembered): connecting again after signing out of the Windows session, the two "Are you trying to sign in to Azure Virtual Desktop Client?" confirmations appeared (the full sign-in no longer repeats), then FreeRDP ended with `ERRCONNECT_ACTIVATION_TIMEOUT [0x0002001C]` (exit 131). Source: `rdp_client_wait_for_activation` (`libfreerdp/core/connection.c:239`) waits `TcpAckTimeout`, default 9000 ms (`settings.c:1268`; option `/timeout:<ms>`, documented "use if you encounter timeout failures"), for the server to finish activation. The cause is not known yet; the log didn't show at which connection state it waited. FreeRDP issue #9870 (Entra authentication, same error) ended without a confirmed cause. The app now logs FreeRDP's connection state changes (`WLOG_FILTER=com.freerdp.core.rdp:DEBUG`; `/log-filters:` doesn't work for this logger because WinPR caches levels at logger creation) to find out.
- 2026-10-17 15:33: each Connect shows Microsoft's page "Are you trying to sign in to Azure Virtual Desktop Client? Only continue if you downloaded the app from a store or website that you trust." twice, once per FreeRDP token request (gateway, then session host). No Microsoft documentation of when this page appears was found (searched 2026-10-17; only forum threads about Android apps). Source facts: FreeRDP skips its gateway token request when `/gateway:…,bearer:<token>` is given (`gateway/arm.c:210–234`, `cmdline.c:4352`), and that token has the app's own client ID and scope (`settings.c:868–874`). The app now passes its access token (renewed first if it expires within 5 minutes), which removes the first request. The session-host token can't be supplied: it is bound to a proof-of-possession key FreeRDP generates per connection (`aad.c:298–316`).
- 2026-10-17: Microsoft's web client (`client.wvd.microsoft.com/arm/webclient`) implements RDSTLS in WebAssembly and uses a different "orchestration" flow; static inspection did not show how it fills the RDSTLS user name and domain, so it can't settle the question.
