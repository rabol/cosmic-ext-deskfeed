## Observations

Dated because these are undocumented Microsoft interfaces.

- 2026-10-17: unauthenticated `GET /organizations/oauth2/v2.0/authorize` with the public client ID returns the normal sign-in page (`sErrorCode` 50058, "not signed in") for every redirect tried, including obviously invalid ones. Redirect validation happens after account selection, so step D needs a real sign-in. An unknown client ID returns 50059 instead.
- 2026-10-17: opening `https://login.microsoftonline.com/common/oauth2/nativeclient?code=…` in a normal browser shows an anti-phishing warning ("This page is not normally shown and could be a sign of a phishing attempt … do not copy or share the URL") and after 3 seconds redirects to `/common/wrongplace`. FreeRDP's terminal `Browse to:` / `Paste redirect URL here:` flow is therefore not usable by people any more. Copying the code with browser developer tools would work around this protection, so we don't use or document it (spec §4 step 4). Consequence: with the public client ID, sign-in needs a web view that catches the redirect before the page loads (as the reference app does), unless the loopback redirect test (step D) succeeds.
- 2026-10-17: a normal browser that is already signed in to another Microsoft account (here a personal Microsoft 365 account) picks that account automatically for the FreeRDP authorize URL, which has no `login_hint`. The app's per-account sign-in cookies (spec §6) avoid this; research tests use a private browser window.

- 2026-10-17 14:23 (the app itself, native build, COSMIC Wayland): sign-in through the WebKitGTK helper with the public client ID, code exchange with PKCE, ID token validation, feed discovery and all tenant feeds succeeded on the owner's account: 3 workspaces, 3 desktops listed. The feed service accepted the public client ID with `X-MS-User-Agent: com.microsoft.rdc.html/2.0.79.2 rdhtml-sdk/2.0.4`.
- 2026-10-17 14:45–14:46 (the app, native build): Connect reached the session host. The AVD gateway token came from our sign-in helper in FreeRDP mode without showing a window (cookies from the app's sign-in). RDSTLS then returned `RDSTLS_RESULT_LOGON_FAILURE [0x0000052E]` with the password pasted into the app's dialog, both with logon setting *Empty domain* and *Automatic* (`AzureAD`). With the reference app's `/d:AzureAD` + pasted password (12:13) the result was the same. Not yet tried: *Entra sign-in* (`/sec:aad`) and a custom (on-premises) domain.
- 2026-10-17 15:04 (the app, debug build): after the owner **changed the password**, a pasted new password still gave `RDSTLS_RESULT_LOGON_FAILURE [0x0000052E]` (retried once, same result). A wrong or mistyped password is now ruled out as the cause. FreeRDP 3.32.2 `arm.c` re-read: the service's `redirectedUsername` always replaces `/u:`, so only the domain is under client control; with `/sec:aad` FreeRDP skips RDSTLS entirely (`arm_fill_gateway_parameters`). Remaining suspects: a policy that blocks password logon to the session host (for example per-user MFA or Conditional Access on Entra-joined hosts without SSO), or session hosts joined to an on-premises domain. Next test: *Entra sign-in*.
- 2026-10-17 15:16 (the app, debug build): **Entra sign-in (`/sec:aad`) connected** to the owner's host pool and showed the desktop, although the `.rdp` file has no `enablerdsaadauth`. This matches the owner's experience with the official Windows and macOS apps, which never ask for a Windows password. The password logon (`0x52E` with every domain setting and a new password) is blocked on the host side; the client can't fix it. Consequences: Entra sign-in is now tried first for every desktop (ADR 0005, revised).
- 2026-10-17 15:16: before the desktop appeared the owner had to sign in 2–3 times (app sign-in, then FreeRDP's gateway and session-host tokens). Cause: FreeRDP 3.32.2 starts a new helper process per token request (`client/common/client.c`, `aad_auth_helper_start` per call), and Microsoft's sign-in cookie is a session cookie that WebKit keeps only in memory. Fix: the helper shares session cookies through `$XDG_RUNTIME_DIR/cosmic-ext-deskfeed-web/` (`signin/src/session_jar.rs`).
- 2026-10-17 15:16: the remote desktop kept its initial size inside a larger window (black area). Cause: COSMIC auto-tiling resizes the window before the display control channel is up, and FreeRDP 3.32.2's SDL3 client sends no layout on the first activation of a windowed session (`client/SDL/SDL3/sdl_disp.cpp`, `OnActivated` returns early when `firstActivation`; `DisplayControlCaps` only makes the window resizable). Any later window resize sends the layout. Upstream fix candidate: send the layout in `DisplayControlCaps` for windowed sessions too.
- 2026-10-17 (refit): the app now watches FreeRDP's display channel logger (`com.freerdp.client.sdl.disp` at DEBUG via `WLOG_FILTER`, a comma-separated list per `wlog.c`). When it logs `DisplayControlCapsPdu: setting the window as resizable` (windowed sessions only), the app maximizes the window with `cosmic-toplevel-management` (`set_maximized`), waits until `cosmic-toplevel-info` reports it maximized, and restores it (`unset_maximized`). In `sdl_disp.cpp` the resulting SDL `MAXIMIZED`/`RESTORED`/`RESIZED` events call `updateMonitor`, which sends the layout once the channel is active; its 1 s retry timer sends the final size. Checked against the owner's COSMIC session with a GTK test window: tile 1524×836 → maximized 3072×1696 → tile 1524×836 within 0.15 s. Still to confirm with a real connection.
- 2026-10-18 (refit, real connection): FreeRDP ran on XWayland (SDL 3.4.18 picks it when COSMIC lacks `wp_fifo_manager_v1`), so the title was mangled and the window had no Wayland app ID; now `SDL_VIDEO_DRIVER=wayland,x11`. Then the refit ran but could be ignored: FreeRDP logs "setting the window as resizable" before its SDL thread applies it, and SDL ignores compositor sizes for a fixed-size window. A refit later on the same window worked (owner confirmed). The app now waits for `SDL_EVENT_WINDOW_RESIZED` (FreeRDP's `com.freerdp.client.SDL` logger at DEBUG) and retries up to 3 times. Maximize/restore made Windows change resolution twice; a focus change away and back (cosmic-comp `src/shell/focus/mod.rs` sends a configure with the size on each activation change) gives one change. Checked with a GTK test window: focus left and returned within 0.15 s, size unchanged in between.
- 2026-10-17 15:33 (the app, Entra sign-in remembered): connecting again after signing out of the Windows session, the two "Are you trying to sign in to Azure Virtual Desktop Client?" confirmations appeared (the full sign-in no longer repeats), then FreeRDP ended with `ERRCONNECT_ACTIVATION_TIMEOUT [0x0002001C]` (exit 131). Source: `rdp_client_wait_for_activation` (`libfreerdp/core/connection.c:239`) waits `TcpAckTimeout`, default 9000 ms (`settings.c:1268`; option `/timeout:<ms>`, documented "use if you encounter timeout failures"), for the server to finish activation. The cause is not known yet; the log didn't show at which connection state it waited. FreeRDP issue #9870 (Entra authentication, same error) ended without a confirmed cause. The app now logs FreeRDP's connection state changes (`WLOG_FILTER=com.freerdp.core.rdp:DEBUG`; `/log-filters:` doesn't work for this logger because WinPR caches levels at logger creation) to find out.
- 2026-10-17 15:33: each Connect shows Microsoft's page "Are you trying to sign in to Azure Virtual Desktop Client? Only continue if you downloaded the app from a store or website that you trust." twice, once per FreeRDP token request (gateway, then session host). No Microsoft documentation of when this page appears was found (searched 2026-10-17; only forum threads about Android apps). Source facts: FreeRDP skips its gateway token request when `/gateway:…,bearer:<token>` is given (`gateway/arm.c:210–234`, `cmdline.c:4352`), and that token has the app's own client ID and scope (`settings.c:868–874`). The app now passes its access token (renewed first if it expires within 5 minutes), which removes the first request. The session-host token can't be supplied: it is bound to a proof-of-possession key FreeRDP generates per connection (`aad.c:298–316`).
- 2026-10-17 (owner): the official Windows and macOS apps never show the "Are you trying to sign in…" page. FreeRDP's authorize URL has no `prompt` parameter (`client/common/client.c`, `aad_auth_request`). Microsoft documents `prompt=none` as "ensures that the user isn't presented with any interactive prompt", returning `interaction_required` (or `login_required`) when that isn't possible (OAuth 2.0 authorization code flow reference). The helper now first sends FreeRDP's request with `prompt=none` in a hidden view, and falls back to the normal sign-in only on those documented errors or after 20 s. It prints the outcome (`cosmic-ext-deskfeed-signin: silent token request (prompt=none): …`) so the next test shows which happened.
- 2026-10-17 (the app): the helper's `prompt=none` attempt for the session-host token returned `interaction_required`; the confirmation page then appeared once (the gateway token now comes from the app, so the second page is gone). With FreeRDP 3.32.2 this page can't be avoided by the app: the helper protocol only returns the sign-in page's redirect, and FreeRDP redeems the code itself with its per-connection proof-of-possession key (`client/common/aad-helper-protocol.md`, `aad.c:298–316`). Microsoft documents getting tokens for other resources with a refresh token at the token endpoint, which needs no page; how the official Windows and macOS apps get this token is not published. Removing the page needs a FreeRDP change (helper supplies the token, or FreeRDP uses a refresh token).
- 2026-10-17 17:07: first start with the saved sign-in (keyring): every workspace feed failed with `refused URL: NotAllowed` (the app's endpoint rules). Not reproduced on the next start (17:17); the app now prints refused URLs (IDs and query removed) to catch it next time.
- 2026-10-17 17:17 and 17:18 (Entra sign-in, after signing out of Windows): `ERRCONNECT_ACTIVATION_TIMEOUT` both times. State log: `NEGO --> AAD` then, exactly 9.0 s later, `AAD --> INITIAL`. The Entra token (and the confirmation page) is fetched before the AAD state starts (`transport.c`, `aad_client_begin`), so the 9 s were spent waiting for the session host's `ts_nonce` or `authentication_result` (`aad.c`); a rejection would have been logged as `Authentication result: …`, and none was. To measure the host's real answer time, the app now passes `/timeout:60000` and prints the state changes live.
- 2026-10-17 17:27 (the app, Entra sign-in, `/timeout:60000`): connected. The AAD exchange took 0.45 s (`NEGO --> AAD` 17:27:19.902, `AAD --> MCS_CREATE_REQUEST` 17:27:20.350), full activation 7.4 s from start including the confirmation page. The earlier 9 s timeouts were therefore not a constant delay; cause still unknown, the 60 s limit stays and the steps are logged live.
- 2026-10-17 17:28 (start with the saved sign-in): discovery returned feed URLs on `rdweb-r1.wvd.microsoft.com` (after interactive sign-ins they were on `rdweb.wvd.microsoft.com`). Microsoft's "Required FQDNs and endpoints for Azure Virtual Desktop" lists `*.wvd.microsoft.com` (TCP 443, service traffic) for client devices. The endpoint rules now accept one host label under `wvd.microsoft.com` for feeds, connection files and icons, with the same path checks; discovery itself stays on `rdweb.wvd.microsoft.com`.
- 2026-10-17 17:36 and 17:40 (the app, Entra sign-in): connected both times. The AAD exchange (`NEGO --> AAD` until `AAD --> MCS_CREATE_REQUEST`) took 49.8 s and 24.3 s (0.45 s at 17:27). This explains the earlier `ERRCONNECT_ACTIVATION_TIMEOUT` with FreeRDP's 9 s default. The app now passes `/timeout:120000`. Why the host sometimes takes this long is not known.

- 2026-10-17 18:12: the desktop opened in full screen although the setting was off. Cause (our bug): the app passed `-f`, but `f` is a FreeRDP *flag* and WinPR's parser turns flags on whatever the prefix (`winpr/libwinpr/utils/cmdline.c`, COMMAND_LINE_VALUE_FLAG). Fixed: `+f` only when wanted, and the connection-file filter drops `screen mode id` and `use multimon`. AAD exchange this time: 54.9 s.

AAD exchange 0.40 s, 0.46 s, 0.44 s (54.9 s at 18:12, 49.8 s and 24.3 s earlier). Not yet known why the shared session cookies weren't accepted in the second case; the helper now logs how many it restored and whether the page was shown.

- 2026-10-17 20:21: the token endpoint's AADSTS70043 text: "The token was issued on 2026-10-17T18:03:33Z and the maximum allowed lifetime for this request is 300" (request at 18:18:10Z). The 300 s matches that setting. Consequence, as the owner observed: a sign-in can be reused for five minutes; after that, app start and Connect need a full sign-in (password and MFA), and within five minutes only the confirmation page appears. Tenant policy; the app handles both cases. **Closed.**
